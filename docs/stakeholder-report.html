Design report · Umeå kommun · October 2026

One place where the municipality's own knowledge answers questions, in Swedish, with sources

Ume.Rag is a knowledge platform for Umeå kommun. Departments point it at web pages, websites and documents. It reads and indexes them, and builds assistants that answer staff questions with links to the exact sources. It runs on the municipality's own servers, and every AI call goes through the LLM gateway the municipality already operates.

One serverThe pilot runs on a single 8-core machine with 16–24 GB of memory.

What it does

Staff ask in plain Swedish and get an answer they can check

Today the answer to a question like "who do I call about IT support?" is spread over thousands of pages on umea.se, the intranet and in PDF files. Ume.Rag gathers those sources per department, keeps them up to date, and lets an assistant answer from them. The assistant shows up as a model in the chat tool staff already use (Open WebUI in the pilot). Other systems, such as the intranet or a case system, can call the same assistant through a standard API.

A department can run as many assistants as it needs, for example one for building permits and one for its own staff handbook. Each one links the knowledge banks it should answer from, and a knowledge bank used by several assistants is fetched and indexed only once. Changes to an assistant are saved as a draft, tested with the assistant's own test questions and then published, and every earlier version can be restored with one click. From phase 2, people and teams can also create their own small knowledge bases by uploading files ("Mina kunskapsbaser"), then ask questions, get summaries and compare documents in the chat.

What happens when a document is added

  1. FetchDownloads the page or file, follows robots.txt and keeps a polite pace (at most 10 requests per second to municipal sites, at night).
  2. CheckSkips anything unchanged since last time. Files are scanned for viruses before anything opens them.
  3. ReadPulls out the real text. Web pages use the site's learned profile; PDFs and Office files go to the document reader, with OCR for scans.
  4. SplitCuts the text into passages of about 400 words' worth of tokens, each labelled with its page title and heading path.
  5. ProtectLooks for personal identity numbers and other personal data. Documents with personal data are kept out of public assistants.
  6. IndexStores each passage twice: as Swedish keywords and as a "meaning" vector, so both exact terms and paraphrases are found.
  7. ReportRuns the collection's test questions and shows how well the right documents are found, before and after the change. One click rolls it back.

What happens when someone asks

  1. Who is askingChecks the person's department and which assistants they may use, from memory, without a database round trip.
  2. UnderstandFor a follow-up like "vad kostar det?", rewrites it into a full question using the conversation so far.
  3. SearchSearches by Swedish keywords and by meaning at the same time, then merges the two result lists.
  4. Enough sources?If nothing relevant is found, it gives a fixed "I can't find an answer" with contact details instead of guessing.
  5. AnswerThe language model writes the answer from the found passages only, citing them. The answer is streamed as it is written.
  6. Remember safelyThe conversation is stored encrypted and deleted after 90 days (pending the archive question below).

Worked example · umea.se

How the platform learns a real website

We checked the design against a real page: Digital omställning och IT. Like most of umea.se it is built in Sitevision, a CMS that many Swedish municipalities use. Most of a web page is menus, footers, cookie banners and share buttons. Indexing all of that is a common reason other platforms give poor answers.

The platform learns this profile on its own from a sample of 30–50 pages. It applies the profile to a new source automatically and shows a before-and-after preview. If the site is redesigned and extraction gets worse, it learns again. A new profile replaces the old one only if no sample page loses real text; otherwise an administrator is asked first. Every profile version can be rolled back with one click.

Safety by design

The classification decides where AI may process the data

Each source, collection and assistant has one of three levels. The platform enforces the level on every AI call, during indexing as well as chat, through the gateway. A call that would go further than its level allows is stopped before any data leaves.

Protecting what people write

  • Chat history is encrypted inside the database. A copied database or backup alone reveals nothing.
  • Kept 90 days by default, then deleted. Destroying the keys so that even backups become unreadable waits for the archive decision (A1 below).
  • No chat or document text ever goes into logs, metrics or caches.
  • Reading another person's conversation needs a reviewer role, a stated reason and an audit entry. For sensitive data a second person must approve.

Failures are visible, never silent

  • Every document gets a record of what happened to it and why.
  • If a sync would delete more than 20 % of a source, or the source suddenly returns nothing, the platform pauses and asks a person.
  • Continuous database backup with point-in-time restore: at most about 5 minutes of data can be lost.
  • A short database outage does not stop chat: the platform keeps using its last confirmed settings for 90 seconds.

Compared with other platforms

Where Ume.Rag is stronger

Before designing anything we studied the source code and issue trackers of five comparable platforms: Eneo (used by several Swedish municipalities), Dify, RAGFlow, Onyx and Open WebUI. The strengths below answer problems we found there.

It understands Swedish

Swedish builds long compound words. Ume.Rag splits them when indexing and when searching, and combines keyword and meaning search. Diarienummer, form names and exact terms are found as well as paraphrases.

None of the five platforms analyses Swedish text. Eneo searches by meaning only, and Open WebUI uses a language-neutral keyword search.

Chat stays fast while it indexes

Answering and indexing run in separate parts with separate resource limits. Before each release, chat speed is measured during a full website crawl plus a scanning batch, and may not get more than 10 % slower.

Eneo runs 78 database queries per message and reached an 11-second wait for the first word at 64 users. Open WebUI freezes during document ingestion.

Small enough to run ourselves

The pilot is six small containers on one server, on the same technology and operations model as the LLM gateway, which the same team already runs. It grows to 3–5 servers for about ten times the pilot's load.

Dify ships 16 containers and about 1,400 settings. Onyx needs 13 containers and at least 10 GB of memory.

Learns each website instead of indexing menus

Learned site profiles find the real content, breadcrumb and date of each site. Pages are fetched again only when the sitemap says they changed, and nothing is re-indexed unless its text changed.

Eneo indexes whole pages including menus and re-embeds every page on every crawl.

Safe with deletions and failures

A deletion guard, a record for every document and degraded-not-green status make problems visible before they cost anything.

Onyx deleted 189,833 documents in one sync and reported success.

Everything is included, and it is ours

Single sign-on, roles, audit log, retention and the admin interface are part of the base platform. It is the municipality's own code with no licence tiers.

Dify keeps SSO and roles closed source. Onyx puts retention deletion in its enterprise edition. RAGFlow has no OIDC, roles or audit in the open version.

Where others are ahead today

  • They exist. Ume.Rag is a finished design with no code yet. The others can be installed today.
  • Breadth. Onyx and Dify have many more connectors and a large plugin ecosystem.
  • Visual building. Dify has a drag-and-drop workflow canvas. Ume.Rag deliberately uses fixed pipelines with settings forms.
  • A polished chat interface. Open WebUI's is much better than anything we would build, which is why the pilot uses it as the front end.

Kept simple on purpose

  • One fixed, well-tested pipeline per source type, set up through forms. A visual workflow builder stays on the list for phase 3 and is built only if editors need it.
  • Search in PostgreSQL, the database the team already runs. A dedicated search engine is added only if measurements show the need.
  • Tools and agents wait until the basic assistant works well (phase 2), and start read-only.
  • Each feature has a clear owner and a measurable reason to exist, which is the opposite of the "kitchen sink" approach.

Roadmap

Four phases, each driven by what the previous one measured

P0 · next

Foundation

A skeleton that builds, deploys, can be monitored and can be restored from backup. Test sign-in, the database with Swedish search, and agreement on one gateway release.

P1

Pilot

One department uses an assistant in Open WebUI. Web pages, websites (umea.se) and file uploads, learned site profiles, quality reports, assistant versions with draft, test and publish, feedback and limited conversation review.

P2

Broaden

More departments, self-service knowledge bases from uploaded files for people and teams, SharePoint, a website widget for citizens, read-only AI tools and MCP, re-ranking for better answers, older file formats, 3 servers with a database standby.

P3

Scale and refine

Driven by measurements: a Swedish benchmark, a dedicated search engine if needed, a Teams client, tools that act on the user's behalf, write actions with confirmation, and a visual pipeline builder if editors need flows the settings forms cannot express.
