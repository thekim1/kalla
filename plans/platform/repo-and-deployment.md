# Platform repository, build and deployment: detailed design

Detail round, step 2. Covers the repository, build conventions, projects, local development, images, production
Compose, release bundle, CI/CD, observability, Kubernetes and the ordered P0 checklist. Builds on [`plan.md`](plan.md)
§1, §2, §7, §10, §11 and [`data-model.md`](data-model.md) (roles, `init.sql`/`app-roles.sql`, migration service, tiers,
Redis prefix, partitions, Hunspell). Choices the plans leave open and contradictions found are in §12.

**Rule**: copy the gateway (`~/git/llmgateway`, commit `e25b491`, release 0.8.5) wherever it fits. Every file below is
marked **copy** (as-is apart from names), **adapt** (same structure, our content) or **new**. Versions marked
*to verify* could not be checked against the gateway or the NuGet check in
[`../../platforms/kernel-memory-and-dotnet.md`](../../platforms/kernel-memory-and-dotnet.md) §5 (NuGet, 2026-10-29).

### 2.3 Frontend (`src/admin-ui`)

- Same `package.json` scripts and toolchain as the gateway: `dev` (Vite), `build` (`vue-tsc -b && vite build`), `test`
  (Vitest), `lint` (`eslint . --max-warnings 0`), `typecheck`. Runtime dependencies copied with the gateway's ranges:
  `vue` ^3.5.43, `pinia` ^4.0.3, `vue-router` ^5.3.1, `@fontsource-variable/geist(-mono)` ^5.3.0, `material-symbols`
  ^0.47.6; dev: `vite` ^8.3.3, `vitest` ^5.0.3, `typescript` ~6.0.3, `tailwindcss` / `@tailwindcss/vite` ^4.3.3,
  `eslint` ^10.12.0 with `eslint-plugin-vue` and `eslint-plugin-vuejs-accessibility`.
- **New** (P2 canvas, admin design §6.8): `@vue-flow/core` 1.48.2 plus `@vue-flow/background` 1.3.2 and
  `@vue-flow/controls` 1.1.3, all MIT, **checked** 2026-10-30 against the package tarballs (version re-checked at P2
  start under the 7-day rule). Justified in `docs/security-and-compliance.md` ("Few direct packages"): transitively
  `d3-drag`, `d3-interpolate`, `d3-selection`, `d3-zoom` and `@vueuse/core` 10.11.1 (+ `@vueuse/shared`,
  `@vueuse/metadata`, `@types/web-bluetooth`, `vue-demi` 0.14.10, whose default build is Vue 3, so `ignore-scripts` is
  safe); nothing else is added for the canvas (no minimap package, no UI kit, no i18n library).
- **Swedish UI**: the gateway's UI texts are English, so `utils/labels.ts`, `utils/problem.ts`, `utils/format.ts` and
  `index.html` (`lang="sv"`) are adapted, not copied; `utils/messages.ts` (error codes → Swedish) is new (admin design
  §4.2, §5.1).
- **Size budget**: a CI build step reports gzip sizes and fails above budget (initial JS ≤ 200 KB, lazy route ≤ 100 KB,
  canvas route ≤ 180 KB; admin design §10.2).
- **npm policy copied unchanged**: `.npmrc` with `ignore-scripts=true`, `min-release-age=7`, `allow-git=none` in
  `src/admin-ui` and `tests/e2e`; `npm ci` only in CI; `npm audit --audit-level=low` fails the build.
- **Design system**: the gateway has no package; it is `src/styles/tokens.css`, `main.css`, `icons.css`,
  `components/ui/*`, `components/layout/*` and `tailwind.config.cjs`. They are copied and listed in
  `src/admin-ui/design-system.lock` (gateway commit + SHA-256 per file). A CI step reports drift as a warning, never a
  failure, so the two UIs stay a family without coupled releases (admin plan, answered question 1).

### 4.3 FakeGateway (not the gateway's FakeLlm)

The gateway's FakeLlm cannot be reused: its `/v1/embeddings` returns **8-dimensional** vectors (`Vector()` takes 8
hash bytes) and it sends no `x-ume-residency` header. `Ume.Rag.FakeGateway` copies `FakeLatency.cs` and the chat
streaming code, and adds:

| Endpoint / behaviour | Purpose |
|---|---|
| `POST /v1/embeddings`: **1024 dimensions**, L2-normalised feature hashing of word unigrams and character trigrams | texts that share words are close, so retrieval and evaluation tests mean something |
| `POST /v1/chat/completions` (stream and not), answers built from the last user message and any `[n]` context, so citation tests can assert; answers Open WebUI task prompts (`### Task:` title/tags/follow-ups) with fixed JSON | chat, condense, `owui-tasks`, evaluation generation and judging |
| Stream modes (chat design §18.4): configurable usage-only final chunk (on/off), broken stream mid-way, stall (> idle timeout), missing `[DONE]`, empty deltas, `finish_reason: length`; echoes `x-ume-session` | streaming edge cases |
| `GET /v1/models`; per-model residency in `appsettings.json` (`OnPrem`, `Eu`, `External`: the gateway's `DataResidency` names) | – |
| Response header `x-ume-residency`; honours `x-ume-max-residency` (case-insensitive names; other values 400 `invalid_request`; `403 max_residency_not_met` if no model fits); records `x-ume-on-behalf-of` and echoes it (gateway design §3, §5.2) | fail-closed tests (plan §6, §7) |
| `GET /v1/catalog/departments` (Data API shape incl. `memberGroups`; department 3000 lists `Byggnadsnämnden`) and `/v1/catalog/teams` (incl. `code`, gateway release C) | organisation sync without the gateway |
| Fault injection: model names `fake-fail-500`, `fake-slow`, `fake-wrong-residency` | resilience and residency tests |
| `FakeGateway:Upstream:Embeddings=http://ollama…` | real BGE-M3 vectors from Ollama when enabled |
| Scripted tool modes (P2): a fixture lists the assistant messages per step (`tool_calls` with ids and arguments, streamed in deltas, or text) | deterministic agent-loop tests (tools design §11.2) |

### 5.5 ClamAV image (`images/clamav/Dockerfile`)

Official ClamAV LTS image plus our `freshclam.conf` and `clamd.conf`. **Decided: no internal mirror**; freshclam uses the official `database.clamav.net` directly (the settings below that mention a mirror are replaced by that). Original proposal: `DatabaseMirror` and `PrivateMirror` =
`${CLAMAV_MIRROR_URL}` (an internal mirror, filled by `cvdupdate` on a host with internet access; owned by IT
operations), `ScriptedUpdates no`, checks 4 times a day; `clamd` on TCP 3310 for the worker (`INSTREAM`),
`StreamMaxLength 60M` (uploads are ≤ 50 MB), `MaxFileSize 60M`, `MaxScanSize 200M`, `ConcurrentDatabaseReload no` on a
16 GB host (avoids doubling memory during reload; scans wait ~30 s) and `yes` on 24 GB. If `database.clamav.net` is
unreachable the signatures age; the worker reads their age with `zVERSION` every 10 minutes (connectors design §11) and
reports `degraded` after 48 h and `unhealthy` after 7 days, and then stops ingesting new files (fail closed).

### 7.3 Rolling updates

`rolling-update.sh` (adapted): pull → **extensions** (`upgrade-extensions.sql`, `ALTER EXTENSION vector UPDATE`, as the
bootstrap user through `docker compose exec postgres`, only when the Postgres image label `ume.rag.pgvector` changed;
the migrator cannot, since it is not superuser) → `run --rm migrations` → replace `rag-api`/`rag-api-b`, then
`rag-admin`/`rag-admin-b`, each only while the other is healthy (gateway logic) → **worker stop-then-start** (no
overlap: its pool would exceed the role's connection limit, and job leases make a short pause harmless) → parser,
renderer, clamav recreated if their image changed (the worker retries the in-flight range).

Migrations are expand/contract only (data-model §10, gateway ADR 017); every release notes *Rolling update: yes/no*.
Postgres image changes that restart Postgres itself are never rolling (a short data-plane outage, announced).

### 7.4 Backup and restore

| What | Tool | Notes |
|---|---|---|
| Postgres | `Backup-Database.ps1` / `Restore-Database.ps1` (copy; `ragdb`, services `rag-api`, `rag-admin`, `rag-worker`, `rag-migrate` must be stopped for restore) | `pg_dump -Fc` inside the container; tiers: run once per tier project |
| Blobs | `backup-blobs.sh` / `restore-blobs.sh` (new): `tar` (or restic, if IT runs it) of `rag-blobs`, **after** the database dump | blobs are envelope-encrypted; keys are rows in `content."DocumentKeys"` |
| Secrets | pepper, `data-protection.pfx`, `secrets/` | separately, through the secret manager (gateway runbook) |
| Master keys | the key service (OpenBao / Key Vault) | **never** the file provider in production |

Consequences of the shred buckets (data-model §7):

1. A database backup holds wrapped data keys; it is readable only while the month's bucket key exists. After the
   bucket key is destroyed, restored conversations of that month are unreadable **by design**.
2. **The key service's own backups must not outlive the shred schedule**: an OpenBao snapshot (or Key Vault backup)
   older than a destroyed bucket would resurrect it. Rule in the runbook: key-service snapshot retention ≤ 30 days, and
   destroyed bucket keys are listed in `audit."AuditLog"` so a restore of the key service can re-destroy them
   (`rag-admin` command `reconcile-shredded-keys` after any key-service restore).
3. After a database restore, the admin runs `reconcile-retention`: deletes `DataKeys` rows whose bucket key no longer
   exists or whose `ExpiresAt` passed, and their conversations; logs counts.
4. Blob/DB skew: blobs without a `DocumentKeys` row are deleted by the worker's orphan sweep; documents whose blob is
   missing are re-fetched on the next sync (uploads cannot be re-fetched: reported in the run).
5. Restore drill (runbook): isolated host, DB + blobs + key service, then a chat history read, a document preview and a
   search query; record RPO/RTO.

## 10. Kubernetes (later; mirrors `docs/kubernetes.md`)

Same shape as the gateway's `deploy/kubernetes`: `base/` (api ×2, admin ×2, worker ×1, migrations Job, probes on
`/health/*`, PodDisruptionBudgets, restricted Pod Security Standard), `components/datastores` (our Postgres image as a

`deploy.sh`. What changes against Compose:

| Compose | Kubernetes |
|---|---|
| internal networks, firewall on bridges | NetworkPolicies: parser ingress only from worker, egress none; crawl egress via an egress gateway or CIDR policy |
| CPU shares, slice | requests/limits, `PriorityClass` `rag-data-plane` > `rag-ingestion`, ResourceQuota per namespace (`ume-rag`, `ume-rag-ingestion`) |
| one host | ingestion on its own node pool (`nodeSelector` + taint); data plane never schedules OCR (plan §2) |
| file blob volume | S3-compatible or Azure Blob only (no RWX volume) |
| Postgres container | our image in the StatefulSet; or CloudNativePG with our image (CNPG's image requirements *to verify*) |
| rolling-update.sh | `deploy.sh`: extensions Job (when needed) → migrations Job → rolling update |
