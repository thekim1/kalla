# Gateway ADR drafts 018–020

Drafts of three rows for `docs/adr.md` in the gateway repo (`~/git/llmgateway`, table at `docs/adr.md:3-23`; append the rows right after 017). They are
copied into the gateway repo when implementation starts, one row with each release (B → 018, C → 019, A → 020; see
[`design.md`](design.md) §8). The numbering follows the release order, not the feature letters of
[`plan.md`](plan.md). Same table and cell style as 013–017: one dense paragraph per cell.

| ADR | Decision | Rationale / consequences |
|---|---|---|
| 018 | A request can lower its own residency ceiling with `x-ume-max-residency`, and never raise it | A key's allowed residencies are set by whoever manages the key (team and department admins included) and can be widened later, so a caller that must keep some data on-prem or in the EU cannot rely on the key alone. Any key may send `x-ume-max-residency: OnPrem \| Eu \| External` (the `DataResidency` names, case-insensitive; no aliases, so `EU` works but `Any` does not: omit the header instead). Anything else, or more than one value, is `400 invalid_request`; ignoring a malformed ceiling would fail open. The ceiling is one more hard constraint in candidate selection, intersected with the key's residencies and the PII on-prem restriction, after routing rules and fallback lists are computed (as ADR 013 requires), so no rule, fallback or retry can go above it. When the ceiling alone removes every candidate the request fails with `403 max_residency_not_met`; there is no silent fallback to a wider residency. It applies to every endpoint that reaches a provider, live sessions and `GET /v1/models` included. `x-ume-residency` keeps reporting where the request went, so a caller that must be sure checks it before using the answer: during a rolling update an older instance ignores the header. Parsing is a span comparison and the intersection a lookup in eight precomputed sets, so the hot path gains no allocation and no round trip. |
| 019 | Department scope can also come from group membership, and admin sign-in refuses other tenants and guests | Municipalities often have no department attribute in their directory, but do have groups. A department gets optional **member groups** (group claim values: Entra object ids, AD FS or Keycloak names, matched case-insensitively like `Oidc:RoleGroups`), edited by gateway admins. At sign-in the scope is the `departmentCodes` claim plus every active department whose member groups the user is in, written back as ordinary `departmentCodes` claims, so every scoped query is unchanged; membership never grants a role. With `Oidc:GroupLookup=Graph` (Entra only) the admin API asks Microsoft Graph `checkMemberGroups` for the member groups the token does not show (groups not assigned to the application, or overage), cached 10 minutes in Redis; it needs `GroupMember.Read.All` and the registration's own client secret. If Graph fails, sign-in continues with claims only (scope can only narrow, never widen), `/bff/user` says `departmentLookup: "failed"` and `admin.group_lookup.failed` (2007) is logged: locking every admin out during a Graph outage would be worse. Member groups are exposed on the Data API's `catalog.read` departments list so another system (Ume.Rag) can apply the same rule with the same data. Independently, `Oidc:TenantId` (token `tid` must match) and `Oidc:RefuseGuests` (default on: `acct = 1` or a foreign `idp`) refuse sign-in and Data API tokens of other tenants and guests (`admin.signin.refused` 2008, `data.token.refused` 3003), because an application registration shared with another system makes a mistaken guest assignment more likely. Keycloak and AD FS emit neither claim, so the guest check is a no-op there; Entra adopters who deliberately admit guests turn it off. |
| 020 | A key can act for listed teams (delegated attribution), and delegation can never widen access | A platform that serves many teams (Ume.Rag) would otherwise hold one key per team: many secrets, and attribution that depends on picking the right one. A gateway admin, and only a gateway admin, gives a key an explicit list of teams; requests from it may send `x-ume-on-behalf-of: <team id or team code>`. The request is then treated as the key acting as a member of that team: the team's request policy, team and department budgets and token quotas, routing rules and usage attribution, while everything that limits access stays the key's own (models, providers, residencies, PII, attachment, provider tools and storage, content guard, address list). Teams have no allow-lists of their own, so the intersection is the key's lists, and routing rules never widen (ADR 013). The key's own budgets and rate limits still cap all its traffic, and key budgets follow the rotation lineage (ADR 007); the delegation list is copied on rotation. Usage records keep the delegating key id, carry the effective team and department and are marked `delegated`, so reports, budgets seeded from usage and exports agree. An unlisted, unknown or inactive team, or the header from a non-delegating key, is `403 delegation_not_allowed` with `gateway.delegation.refused` (1006). The list is checked when the key is loaded into the authentication cache (one extra query on a cold load, none per request) and refreshed by the existing key invalidation, which team and department changes already publish. Because a delegating key acts across departments, its settings can only be changed by gateway admins; a team on a list cannot be deleted until it is removed from the list (a grant is not orphaned like a rule under ADR 014). End users stay invisible to the gateway: per-user limits remain the calling platform's job. |
