# Plans

One folder per service or cross-cutting area, each with a `plan.md` (first-level plan) and the detail documents of
detail steps 1–10 (`platform/data-model.md`, `platform/repo-and-deployment.md`, `*/design*.md`,
`gateway-changes/adr-drafts.md`); where a plan and its design differ, the design wins. Background:
[`../01-general-idea.md`](../01-general-idea.md) (design and decisions),
[`../platforms/00-comparison.md`](../platforms/00-comparison.md) (lessons from Eneo, Dify, RAGFlow, Onyx, Open WebUI,
Kernel Memory and OpenSearch) and [`../02-architecture-review.md`](../02-architecture-review.md) (improvements R1–R7,
now applied to these plans).

Cross-cutting passes, in order: [`consistency-pass.md`](consistency-pass.md) (detail step 11),
[`performance-pass.md`](performance-pass.md) (≈ 10× the pilot on 3–5 hosts: capacity model, bottlenecks, topologies,
scaling triggers, scale test) and [`simplification-pass.md`](simplification-pass.md) (thin P0/P1, fixed pipelines,
stock Postgres, backups and key escrow, residency by structure, one gateway release, advisory evaluation, umea.se
findings and learned site profiles, six containers in the pilot, many assistants per department: assistant versions
and a derived mode). Where the simplification pass and an older passage differ, the simplification
pass wins. [`weakness-review.md`](weakness-review.md) is binding over both (§1: P1 split into P1a walking skeleton and
P1b pilot hardening; site-profile learning, shared frontier, answer judge, effect-tag publish plans, adaptive
embedding and the assistant extras move to P2).

Decisions put off on purpose, with their stopgaps and deadlines: [`postponed-decisions.md`](postponed-decisions.md)
(reviewed at the start of every phase). Package, behaviour and estimate checks from every document's "To verify"
section, with phase and method: [`to-verify.md`](to-verify.md).

Architecture diagrams (Mermaid: system overview, chat request, ingestion and publishing, agent tool call):
[`architecture.md`](architecture.md).

Plain-language overview for stakeholders: [`../docs/stakeholder-report.html`](../docs/stakeholder-report.html) (open
in a browser).

Working name for the platform and its code: **Ume.Rag** (placeholder, to be renamed).

## Phases (all areas)

| Phase | Goal | Scope |
|---|---|---|
| **P0 Foundation** | Skeleton that builds, deploys, is observable and can be restored | Repo, Aspire AppHost, ServiceDefaults and health, migrations with config outbox, config-version library with the grace window, Postgres image (stock pgvector + pgBackRest) + .NET decompounder test, pgBackRest with WAL archiving, backups from a host timer and a point-in-time restore drill, resource zones, Keycloak with the gateway's claims, gateway-style keys, FakeGateway, parser contract, worker dispatcher skeleton, admin UI skeleton and write path, single-host Compose, `verify.yml` + `release.yml` + image test, deploy to the test host; scale seams (pooler-safe SQL, write-once `IBlobStore`, `IJobQueue`, `Worker:Classes` and `Worker:Concurrency:<class>`); Entra package 1 (RAG's own registrations) submitted; combined gateway release agreed (ADR drafts 018–020); DPIA (register G1) started with the data protection officer and A1 given a named owner ([weakness review §4](weakness-review.md#4-data-protection-guards-the-secondary-copy-while-the-primary-stays-unprotected)) |
| **P1a Walking skeleton** ([weakness review §1](weakness-review.md#1-p1-builds-a-platform-before-anyone-sees-one-good-answer)) | A member of the pilot department asks a question in Open WebUI and gets a cited answer from umea.se content | URL list, umea.se crawl (full traversals until a 500-URL sample shows sitemap `lastmod` reliable, then `lastmod` incremental runs, [weakness review §3](weakness-review.md#3-outdated-or-removed-content-keeps-being-answered); one crawl frontier per source; the umea.se site profile is a hand-checked Sitevision preset, a manual profile JSON versioned like any config) and file upload, each through its one fixed pipeline with template parameters; formats HTML, PDF (text layer and OCR, every PDF through the parser), modern Office, OpenDocument, images (Tesseract `swe`), text, Markdown, CSV; auto-parse rules; personal-data patterns with a gated name check; on-prem platform embedding profile (fixed embedding concurrency and range sizes from configuration); hybrid retrieval with citations, a not-found gate (vector side alone until the keyword floor is calibrated) and an `IReranker` seam; the **pilot gold set** ([weakness review §2](weakness-review.md#2-nothing-proves-the-answers-are-good-and-not-found-is-effectively-off-at-launch): 100–150 answerable, 30–50 unanswerable and ≥ 10 temporal questions written with the pilot department, stored as `human` evaluation questions, start of register B1) run through the retrieval evaluator three ways (vector-only, hybrid, hybrid without the decompounder; hybrid and the decompounder stay only if they beat vector-only) and used to calibrate both not-found thresholds; Chat API with citations and an explicit residency ceiling on every gateway call; Open WebUI title, tag and follow-up generation off; one assistant (instructions + directly linked collections) for the pilot department; `GatewayModels` sync; client registry with Open WebUI at ceiling `internal`; department scope from groups in the claim; single host, one slot, six long-running containers (`rag-api`, `rag-admin`, `rag-worker`, `rag-parser`, `rag-clamav`, `postgres`; no Redis: rate limits and the query-embedding cache in process, admin sessions in Postgres) |
| **P1b Pilot hardening** | One pilot department uses an assistant in Open WebUI | Preview; advisory evaluation harness (publish = re-process every document of the collection, unchanged stages free from the per-stage caches → report → keep or roll back; nightly runs); assistants edited as drafts and published as versions, with history and restore (skills arrive in P2); 90-day metadata retention (the pilot assistant runs history mode `none` until A1 is answered: metadata and ratings only, no message content, no chat bucket keys, content encryption or conversation review in P1, [weakness review §4](weakness-review.md#4-data-protection-guards-the-secondary-copy-while-the-primary-stays-unprotected)); feedback (ratings) with Open WebUI import (HTTP API) and the feedback page; the DPIA (register G1, started in P0) finished before go-live; a fixed Open WebUI banner against confidential input; a runbook section for public-records requests answered from Open WebUI's copy; Swedish admin journey pages for sources and the assistant (generic forms for platform objects); `perf.yml` (R1) and nightly evaluation; one combined gateway release (residency ceiling, delegation, member groups claims-only); the go-live gate, freshness rules and data-protection items of [weakness review](weakness-review.md) §2–§4 (go-live gate: department reviewers grade the gold-set answers by hand, once, against correct answers ≥ 80 %, citation precision ≥ 90 %, false not-found ≤ 10 %, off-topic answered "not found" ≥ 80 %; evaluation reports lead with the gold set, publish stays advisory; **pilot success** = the gate met at go-live and at the end of the pilot, re-run monthly, and the department decides to continue; freshness, [weakness review §3](weakness-review.md#3-outdated-or-removed-content-keeps-being-answered): per-collection age decay, on for PDFs in the `website` template, `demote` URL patterns, traversal completeness by ratio (≥ 99 % of seeds resolved), a removal check for URLs leaving the sitemap, the 500-URL `lastmod` sample) |
| **P2 Broaden** | Several departments, internal sources, tools; first multi-host deployment | Moved from P1 ([weakness review §1](weakness-review.md#1-p1-builds-a-platform-before-anyone-sees-one-good-answer)): assistant version diff, per-assistant test-question sets, assistant templates and copy, the department map and unused-assistant attention items, site-profile learning with automatic re-learning (adds to the manual profiles), the crawl frontier shared between sources (claims, releaser), the nightly answer judge (`answers` runs), publish plans from effect tags, adaptive embedding concurrency (AIMD) and moving-average range sizing; SharePoint; renderer (only if pilot-start checks show sources need JavaScript); legacy `.doc`/`.xls`/`.ppt`, RTF and e-mail, archives and macro-enabled Office (register Z1); parse-profile proposals with platform-admin approval; rerank (a separate P2 gateway release with an endpoint for `bge-reranker-v2-m3` on-prem); Graph member-group lookup with data-plane audiences and approval package 2; skills with know-how and tools, never collections (advisory skill gate run in `rag-admin`); an assistant linking a tool-bearing skill runs the agent loop (derived mode, no assistant type to choose); owner-team edit scoping per department; `/mcp` with `search_knowledge` and `list_collections` early; in-process tool hub (`hosted` servers only) with read-only tools; first municipal server `ume-mcp-kommun` (mock fee calculator); sharing with named departments; public widget; stored chat content when A1 allows it (history modes `stored`/`session`, chat bucket keys, content encryption, crypto-shredding if A1 allows deletion, conversation review incl. search and the `sensitive` two-person flow; weakness review §4); chat attachments (chat-scoped); multi-host topology with its seams (`LeaderLeases`, connection-budget script, batched dequeue, debounced `NOTIFY`, Redis for shared rate limits, the query-embedding cache and crawl and embedding leases, a/b slots); Postgres streaming standby before production beyond the pilot; `flake-hunt.yml`, `scale.yml`, parser fuzzing |
| **P3 Scale and refine** | Driven by measurements | Swedish benchmark (curated evaluation layer), OpenSearch if a trigger fires, separate `rag-tools` service with the first external, OBO or write tool, `municipal`/`external` tool hosting and tool egress, per-skill MCP endpoints and `ask_assistant`, Teams client, Entra OBO for user-delegated tools, write tools with confirmation, visual pipeline builder if its trigger fires (register C2) |

Order within P1: P1a: pilot-start checks (source inventory: legacy formats, JavaScript need; the existing umea.se chat,
register W1) → platform + identity → combined gateway release (parallel, gateway repo; the pilot waits for it) → parser
+ ingestion worker → knowledge API → chat API → crawler with the hand-checked Sitevision preset (umea.se acceptance
page) → one assistant in Open WebUI (P1a done: a first cited answer); the pilot gold set is written in parallel from
the pilot-start checks on and run three ways once the crawl is in (weakness review §2). P1b: admin journey pages → evaluation harness and
`perf.yml` → Open WebUI pilot (the DPIA G1, with W2 on Open WebUI chat-copy retention inside it, finished before it; A1 needs a named owner before P0 ends but no longer blocks the pilot, which runs history mode `none`, weakness review §4).
